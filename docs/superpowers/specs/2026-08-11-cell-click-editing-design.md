# 달력 칸 클릭 편집 + 패널 탭 — 설계

작성일: 2026-08-11

## 1. 개요

두 가지를 함께 다룬다. 둘 다 오른쪽 편집 패널의 같은 자리를 건드려서, 따로 설계하면 서로를 참조하게 된다.

1. **달력 칸을 클릭해서 그 날짜를 편집한다.** 지금은 패널 맨 아래에 31일치 입력 블록이 세로로 늘어서 있어, 24일을 고치려면 내보내기·테마·배경·스티커·폰트·제목·규칙을 전부 지나쳐 스크롤해야 한다. 화면에는 달력 미리보기가 이미 떠 있는데 그걸 클릭할 수 없다.
2. **패널을 탭 3개로 접는다.** 지금 섹션이 13개다 — 이미지 저장 · 년·월 · 테마 · 배경 이미지 · 스티커 · 폰트 · 제목 · 목표 상자 · 할 일 상자 · 메모 상자 · 반복 일정 · 날짜별 일정 · 저장 공간.

**PC를 기준으로 설계한다.** 폰은 동작하되 최적화 대상이 아니다. 이 결정이 아래 여러 항목의 근거가 된다.

## 2. 결정된 사항

브라우저에 목업을 띄워 사용자가 직접 고른 값이다.

| 항목 | 결정 |
|---|---|
| 편집 진입 | 미리보기 달력 칸 클릭 |
| 31일 목록 | **없앤다** |
| 편집기 형태 (PC) | **칸 옆 팝오버** |
| 편집기 형태 (폰) | **바텀시트** |
| 초기 상태 | 아무 날짜도 안 고른 상태로 시작 |
| 패널 구조 | **탭 3개** — 달력 / 꾸미기 / 사이드바 |
| 이미지 저장 | **탭 밖**, 패널 맨 위 |
| 저장 공간 | 패널 맨 아래 한 줄 |

### 2.1 왜 PC에서 팝오버인가

후보가 셋이었다. 패널 맨 위 고정 / 패널 하단 붙박이 / 칸 옆 팝오버.

앞의 둘은 서로 트레이드오프를 주고받는다. **위에 두면** 결과가 항상 같은 자리에 오지만 탭 줄이 280px 아래로 밀려, 810px 패널에서 설정이 쓸 세로가 3분의 1 넘게 깎인다. **아래 두면** 탭이 위에 붙지만 클릭한 곳(달력 중간)과 결과가 뜨는 곳(패널 맨 아래)이 화면에서 대각선으로 가장 먼 두 지점이 된다.

**팝오버는 패널을 아예 안 건드려서 두 문제가 동시에 없어진다.** 탭이 세로를 100% 쓰고, 「아무것도 안 골랐을 때 그 자리에 뭘 보여줄까」라는 문제도 사라진다 — 안 고르면 팝오버가 없을 뿐이다.

### 2.2 폰은 왜 다른가

팝오버는 폰에서 못 쓴다. 화면 폭이 390px인데 팝오버가 320px이라 달력을 거의 다 덮는다.

**폼은 한 벌이고 껍데기만 둘이다.**

```
SelectedDayEditor        폼 (일정 · 추가 문구 · 아이콘 · 강조 · 넘침 경고)
  ├ 넓은 화면 → 팝오버 껍데기   (칸 옆, 방향 뒤집기)
  └ 좁은 화면 → 바텀시트 껍데기 (화면 하단 고정)
```

편집 UI를 두 벌 유지하는 것과는 다르다. 앞으로 날짜 편집에 무엇을 더해도 고칠 곳은 `SelectedDayEditor` 한 곳이다.

## 3. 동작 명세

### 3.1 선택 상태

`selectedDate: string | null`을 `App`의 지역 상태로 둔다. **`ScheduleDoc`에 넣지 않는다.** 저장 대상이 아니고, 문서에 들어가면 `migrateDoc`과 마이그레이션 테스트가 전부 이 값을 알아야 한다.

- 초기값 `null`
- **달을 바꾸면 `null`로 되돌린다.** 8월 8일을 고른 채 9월로 넘어갔을 때 9월 8일이 선택돼 있는 것은 자연스럽지 않다

### 3.2 고르기와 해제

| 동작 | 결과 |
|---|---|
| 그 달 날짜 칸 클릭 | 선택 |
| 앞뒤 달 칸(흐린 26~31일) 클릭 | **무시.** `days`에 저장되지 않는 날짜라 편집 대상이 없다 |
| 같은 칸 재클릭 · `✕` · `Esc` · 팝오버 바깥 클릭 | 해제 |

선택된 칸은 오버레이가 파란 테두리로 표시한다. 팝오버가 그 칸을 덮을 수 있으므로 화살표와 별개로 테두리를 유지한다.

### 3.3 이동

`‹ ›`는 **그 달 1일부터 말일까지만** 움직인다. 1일에서 `‹`, 말일에서 `›`는 비활성이다.

달을 넘기지 않는 이유: 달 전환은 이미 `MonthPicker`의 일이고, 문서를 통째로 갈아끼우는 무거운 동작이라 화살표 한 번으로 일어나면 놀랍다.

### 3.4 폼 내용

지금 `DayEditor`의 한 항목과 같다 — 일정 텍스트, 추가 문구, 아이콘, 강조 3줄, 넘침 경고.

**아이콘 3×3 그리드는 항상 펼친다.** 접이식으로 만든 이유가 "31개가 동시에 펼쳐지는 걸 막기 위해"였는데(`DayEditor.tsx` 주석), 한 날짜만 남으면 그 이유가 사라진다. 클릭이 한 번 줄어든다.

**폼 크기**: 헤더 30 + 일정 60 + 추가 문구 50 + 아이콘 190 + 강조 90 + 패딩 ≈ **420px 높이**. 가로는 강조 줄이 가장 넓다 — 라벨 56 + 버튼 7개×22 + 간격 6×6 = 246px. 좌우 패딩을 더해 **팝오버 폭 320px**로 잡는다. 지금 패널 폭(320~420px)과 비슷해 폼을 그대로 옮겨도 안 깨진다.

### 3.5 팝오버 (넓은 화면)

- 선택된 칸에 붙어 뜬다. 칸을 가리키는 화살표를 갖는다
- **방향 뒤집기**: 열 인덱스가 오른쪽에 치우치면 왼쪽으로, 행 인덱스가 아래에 치우치면 위로 펼친다
- **화면 안으로 밀어넣기(clamp)**: 뒤집어도 창 밖으로 나가면 화면 안으로 민다. 창을 좁혔을 때 필요하다

### 3.6 바텀시트 (좁은 화면, ≤900px)

- 화면 하단에 `position: fixed`로 붙는다. `.app-editor`에 `transform`이 없어 정상 동작한다
- **최대 높이는 화면의 75%, 내용이 넘치면 시트 안에서 스크롤한다.** 폼이 420px이라 작은 폰(667px)에서 55%(367px)로는 안 들어간다
- 시트가 달력 아랫줄(23~31일)을 가리는 것은 남는 대가다. 가려진 날짜는 `‹ ›`로 도달할 수 있고 `✕`로 언제든 치운다

### 3.7 저장

기존 `updateDay`와 400ms 자동 저장을 그대로 쓴다. 새로 만들 것이 없다.

## 4. 패널 탭

### 4.1 묶음

| 탭 | 내용 |
|---|---|
| **달력** | 년·월(지난달 가져오기 포함), 반복 일정 |
| **꾸미기** | 테마, 배경 이미지, 투명도, 폰트, 스티커 |
| **사이드바** | 제목, 목표 상자, 할 일 상자, 메모 상자 |

**탭 밖**: 이미지 저장(맨 위), 저장 공간(맨 아래 한 줄).

이미지 저장을 탭에 넣지 않는 이유는 `ExportPanel`을 맨 위에 둔 기존 판단(`EditorPanel.tsx` 주석: "가장 자주 쓰는 기능이라 맨 위에 둔다")을 뒤집지 않기 위해서다. 탭의 약점은 "안 보이는 탭에 뭐가 있는지 모른다"인데, 매번 쓰는 것을 밖에 꺼내 두면 그 약점이 닿는 범위가 줄어든다.

편집기가 팝오버로 나가면서 **패널에 탭 밖 고정 요소가 이미지 저장 하나만 남는다.** 탭 줄이 화면 중간에 놓이는 문제가 없어진다.

### 4.2 사이드바 탭

`HeaderEditor.tsx` 한 파일이 이미 제목·상자 3개를 전부 갖고 있다. 화면에서만 네 섹션으로 흩어져 있었으므로 파일을 쪼갤 필요가 없다.

### 4.3 탭 상태

고른 탭을 localStorage에 저장해 새로고침해도 유지한다. 저장 키는 `weekplanner:editor-tab`.

`ScheduleDoc`에 넣지 않는다 — 결과 이미지에 영향을 주지 않는 편집기 상태다.

## 5. 발견 가능성

31일 목록이 사라지고 팝오버라서 안내 카드가 놓일 자리도 없다. **칸을 클릭할 수 있다는 단서가 필요하다.**

**PC — 호버 표시.** 칸에 마우스를 올리면 커서가 손가락 모양으로 바뀌고 옅은 테두리가 뜬다. 클릭을 받는 오버레이에 몇 줄이면 된다.

**폰에는 단서가 없다.** 호버가 없기 때문이다. PC를 기준으로 설계하기로 한 결과이며, 3장의 알려진 제약에 남긴다.

### 6.1 DayEditor는 대부분 사라진다

`DayEditor.tsx` 298줄 중 복잡한 부분이 **전부 "31개라서" 있는 것**이다.

| 없어지는 것 | 있던 이유 (주석에 적혀 있음) |
|---|---|
| `memo`로 감싼 `DayBlock` | "31일치 블록이 전부 다시 그려진다" |
| `useCallback` 3개 | memo를 무력화하지 않으려고 고정 |
| `openIconPicker` 상태 | "31개 블록이 각자 열려 있으면 감당 못 할 길이" |
| `IconPicker`의 접이식 로직 | 같은 이유 |

실제로 쓸모 있는 폼은 `DayBlock` 60줄이고, 이미 `(date, entry, theme, onPatch)` props로 분리돼 있어 그대로 들어낸다. `SwatchRow`(56줄)와 `IconPicker`의 그리드 부분은 유지한다.

**폼이 화면 크기에 따라 두 모습을 갖지 않게 한다.** 아이콘 접이식을 폰에서만 살리면 `openIconPicker` 상태가 되살아나므로, 시트 스크롤로 푼다(3.6절).

### 6.2 오버레이

**클릭 수신은 좌표를 계산하지 않는다.** 오버레이도 `CalendarGrid`와 같은 구조의 CSS 그리드(`repeat(7, 1fr) / repeat(6, 1fr)`)로 만들고, 필요한 숫자는 격자 영역의 위치와 크기 4개로 줄인다. 안쪽은 브라우저가 똑같이 나눈다.

`layout.ts`에 더한다.

```ts
export const CELL_AREA_X = OUTER_PADDING + SIDEBAR_WIDTH + COLUMN_GAP + BORDER_WIDTH
export const CELL_AREA_Y = OUTER_PADDING + BORDER_WIDTH + DOW_ROW_HEIGHT
export const CELL_AREA_WIDTH = GRID_INNER_WIDTH
export const CELL_AREA_HEIGHT = GRID_INNER_HEIGHT - DOW_ROW_HEIGHT
```

**축소 처리는 `StickerDragLayer`와 다르게 간다.** 스티커 레이어는 좌표마다 `* scale`을 곱하는데, 오버레이는 루트에 `transform: scale(s)` 한 번만 걸고 안쪽은 전부 캔버스 좌표(px)로 쓴다. `PreviewStage`가 캔버스에 하는 것과 같은 방식이라 정렬이 어긋날 여지가 없다.

선택·호버 테두리는 같이 축소되면 0.3배에서 안 보이므로 `Math.round(4 / scale)` 캔버스 px으로 그려 화면에서 4px이 되게 한다.

**배치 순서**: `App`에서 `DayClickLayer`를 `StickerDragLayer`**보다 먼저** 놓는다. 반대로 두면 오버레이가 스티커 위에 깔려 스티커를 못 끈다. 루트는 `pointerEvents: 'none'`, 각 칸만 `'auto'`다.

**오버레이는 `canvasRef` 바깥에 있다.** `html-to-image`는 `canvasRef`가 가리키는 `ScheduleCanvas` 노드만 직렬화하므로 선택 테두리가 내보낸 PNG에 들어갈 수가 없다. 조심해서가 아니라 구조상 불가능하다.

### 6.3 팝오버 위치 — 여기에만 좌표 계산이 생긴다

클릭 수신은 CSS 그리드라 좌표가 없지만, **팝오버를 어디에 띄울지는 화면 좌표가 필요하다.** 두 계산이 공존한다.

```ts
cellScreenRect(index: number, scale: number): { x, y, width, height }
popoverPlacement(col: number, row: number): { horizontal: 'left' | 'right', vertical: 'below' | 'above' }
```

**팝오버를 오버레이 안에 넣고 역스케일하는 방법은 쓰지 않는다.** 좌표 계산이 0이 되지만, CSS `transform`이 걸린 컨테이너 안의 입력칸에서 **한글 IME 후보창 위치가 틀어질 수 있다.** 모든 입력이 한글인 앱이라 가벼운 위험이 아니다.

`cellScreenRect`가 `CalendarGrid`의 CSS 그리드와 따로 노는 두 번째 계산이 되는 것은 이 선택의 대가다. 7장의 테스트로 못박는다.

미리보기 스크롤·리사이즈 추종은 오버레이와 같은 컨테이너에 있어 자동으로 된다.

### 7.2 수동 (`docs/manual-checklist.md`에 추가)

1. **미리보기를 축소한 상태에서 눈에 보이는 칸과 실제로 눌리는 칸이 같은지** — 창 폭을 바꿔가며. 정렬 문제라 자동 판정이 안 된다
2. **팝오버 안 입력칸에서 한글이 정상적으로 입력되는지** — IME 후보창 위치 포함
3. 가장자리 칸(토요일 열, 마지막 주)에서 팝오버가 뒤집혀 뜨는지, 창을 좁혔을 때 화면 안에 들어오는지
4. 날짜를 고른 상태로 PNG를 내보내 **파란 테두리가 없는지**
5. 스티커가 있는 칸에서 스티커가 여전히 끌리는지
6. 폰 폭에서 시트가 올라오고 닫으면 선택이 풀리는지, 폼이 시트 안에서 스크롤되는지

## 8. 안 만드는 것

- **넘침 경고 요약 줄** — 한 칸에 98자(추가 문구가 있으면 70자)를 넘겨야 뜨는데 흔한 입력이 아니다. 고른 날짜 폼 안의 기존 경고는 그대로 둔다
- **실행 취소** — 별개 주제다
- **화살표 키로 날짜 이동** — `‹ ›` 버튼으로 충분하다
- **선택 상태 저장** — 세션 상태다

## 9. 알려진 제약

| 항목 | 내용 |
|---|---|
| 폰에 클릭 단서가 없다 | 호버가 없기 때문. PC 기준 설계의 결과 (5장) |
| 폰에서 칸이 39×31px | 손가락으로 정확히 눌러야 한다. 지금은 목록으로 편집해 필요 없던 요구 |
| 시트가 달력 아랫줄을 가린다 | `‹ ›`로 도달 가능 (3.6절) |
| 팝오버가 옆 칸을 가린다 | 8일을 편집하는 동안 15·22일 근처가 안 보인다 |
| 좌표 계산이 두 벌 | 클릭은 CSS 그리드, 팝오버는 `cellScreenRect`. 테스트로 묶어 둔다 (6.3, 7.1) |
